# The testmo-suite-designer agent and design-test-cases skill

What these two files do, how they relate, and where they sit next to the automated BDD
pipeline the rest of this repo is about. If you only came here for one paragraph:
**this is the manual-testing lineage, not the automated one** — it produces Testmo test
cases for QA to run by hand, not `pytest` code.

---

## Why a separate lineage

Everything else documented in `docs/ARCHITECTURE.md` — `app-cartographer`,
`feature-test-designer`, `test-case-auditor` — exists to crawl a live app and generate
*automated* BDD suites from what the crawl observes. That pipeline cannot know anything
the app doesn't show it live: a remote-config default, a PRD's stated intent, an
events sheet's parameter names.

`testmo-suite-designer` is the other half of QA's work: turning a BRD, a Figma file, a
remote-config table, and reviewer comments into a **manual** Testmo suite a human tester
runs. It doesn't touch `context/`, doesn't drive a device, and doesn't share a code path
with the crawler. The only thing it shares with the rest of the repo is the discipline —
never guess, cite the source, flag what's unconfirmed.

## The skill: `design-test-cases`

Lives at `.claude/skills/design-test-cases/`. Produces manual test cases for the group's
native iOS/Android apps — Bayut UAE, Bayut KSA, Bayut Egypt, Bayut GCC, Dubizzle Egypt,
Dubizzle GCC, Zameen PK, OLX PK, Hatla2ee — in the Given/When/Then house style QA uses in
Testmo. Mobile only; it will not write web test cases.

It covers two different jobs, run through two different documents:

| Job | When | Document |
|---|---|---|
| **Design** a suite from nothing | No suite exists yet, or it's being replaced wholesale | `SKILL.md` Phases 0–9 |
| **Review** an existing suite | A suite is already in Testmo and reviewer comments are coming in case by case, or it needs trimming | `references/reviewing-existing-suites.md` |

### Designing from nothing (Phases 0–9)

The short version of the flow in `SKILL.md`:

0. **Identify the app**, read its knowledge base in `references/apps/<app>.md` in full —
   this is where per-app facts (languages, device matrix, deeplink domains, confirmed
   remote-config contracts, terminology) live, so the same procedure produces
   app-correct cases every time.
1. **Intake** whatever's supplied — BRD, ticket, Figma, tracking sheet — and say plainly
   what's missing rather than working around a gap.
2. **Build a numbered requirements ledger** from every testable statement. Every case
   traces back to a ledger line; every ledger line without a case gets flagged, not
   silently dropped.
3. **Clarify first.** Blocking ambiguity gets asked about, in one batch, before any case
   is written. This is the rule the skill's own learnings log breaks most often when
   skipped.
4. **Design the feature-specific cases**, working an eleven-point checklist (trigger and
   gating → content → interaction → validation → submission → frequency/cooldown →
   persistence → runtime config changes → error paths → cross-context edge cases →
   regression on untouched behaviour).
5. **Append mandatory cross-cutting scenarios** from `references/common-scenarios.md`,
   tailored to the feature's actual surfaces.
6. **Self-review** — three fields present, falsifiable Expected Results, valid Gherkin,
   assertion order matches Then order, no duplicate cases, full ledger coverage.
7. **Report**, don't recite — count, coverage, assumptions, open questions. Never dump
   the full case set into chat.
8. **Export the CSV** via `scripts/sheet_tools.py` — the same ten-column shape every
   time, generated by script rather than hand-typed so it can't drift from spec.
9. **Hand off for human review** (Notion) — the skill never uploads to Testmo itself.

### Reviewing an existing suite

A different shape of work, covered in `references/reviewing-existing-suites.md`: taking
an already-uploaded suite through a live cycle of reviewer comments, one at a time, and
optionally trimming it afterward. Each comment gets classified — clear, ambiguous, or
contradictory — before anything is touched:

- **Clear** comments get applied directly, after checking whether the fix is a small
  refinement or a *premise reversal* (the comment contradicts the case's core assertion,
  not just a detail — the whole scenario gets rewritten, not just the disputed line).
- **Ambiguous** comments never get pattern-matched from how a similarly-worded past
  comment was resolved — the plausible readings get named and the person gets asked.
- **Contradictory** comments (two reviewer notes that can't both be right) get surfaced
  as an open question, never silently resolved in one direction.

Two housekeeping passes are offered at natural checkpoints: **testability triage**
(collecting every case blocked on something external — a bucket-forcing mechanism, a
second device — into one pre-flight list) and **reduction** (safe cuts and merge
candidates, always with the coverage tradeoff named, never applied unprompted).

## The agent: `testmo-suite-designer`

Lives at `.claude/agents/testmo-suite-designer.md`. It's the skill's dedicated,
repeatable worker — same inputs in, same discipline applied, same output shape, whether
it's session one on a brand-new feature or session forty reviewing comment sixty on an
existing suite.

**Mode is decided from what's actually supplied, not assumed from the first message.**
If an existing export CSV or reviewer comments are in the mix, that's REVIEW mode even if
a PRD is also mentioned. A single engagement is often both, in sequence: DESIGN produces
the baseline suite, it goes to Testmo, comments come back over following sessions, REVIEW
applies them.

### Hard rules the agent enforces on itself

1. **Never guess.** Ambiguity is flagged, not pattern-matched from a similar past case.
2. **Never fabricate a source.** An Expected Result with nothing behind it —
   no PRD line, no Figma frame, no confirmed knowledge-base fact — is marked
   `[ASSUMED — needs verification]`, visibly.
3. **Re-read, don't recall.** In REVIEW mode, a reported "fix applied" gets verified by
   re-reading the actual current case, not trusted at face value.
4. **Keep internal citations out of case text.** Reasoning that cites a knowledge base or
   a past decision belongs in the response to the person, never inside a case's
   Given/Then clause.
5. **Never upload to Testmo.** Not even on request — uploading is `upload-to-testmo`'s
   job specifically because Testmo has no update or delete API, and review-after-upload
   is not a safety net for a permanent create.
6. **Route durable corrections to the knowledge base**, not just the current suite — a
   terminology fix or confirmed remote-config contract goes into `apps/<app>.md` via
   `update-knowledge` so the *next* suite already knows it.
7. **Say plainly when something can't be produced** — no Figma access, no knowledge base
   for the requested app, a blocking question with no answer — rather than producing a
   plausible-looking suite around the gap.

## Where this came from

Both the `reviewing-existing-suites.md` reference and several entries in
`references/learnings.md` (L-010 through L-013) trace back to one real cycle: reviewing
an ~80-case Bayut UAE suite for the Recently Viewed Properties feature. That review is
also where the confirmed Remote Config contract and device-local-storage facts now
recorded in `references/apps/bayut-uae.md` came from — captured once, during a real
review, so the next suite for that app doesn't have to re-derive them.
