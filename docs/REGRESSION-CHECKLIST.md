# Regression Checklist — Bayut UAE (human-authored)

**Source.** Provided directly by the manual QA team as `Bayut UAE - Regression Checklist.pdf`
and transcribed here verbatim (reformatted from a 3-column table into a Markdown
checklist; no content added or removed).

**What this is, and what it is not.** This is **not** an `app-cartographer` output. Every
other file in `context/` is generated by crawling the live app and tagged `[OBSERVED]` /
`[ASSUMED — verify]` per D-009. This file is different: it is the manual QA team's own
accumulated knowledge of the real app, presumably more current and more accurate than
anything this programme has observed so far, since no device has ever been connected
(`docs/PROJECT-STATE.md` §0). Treat it as a high-trust human source, not as unverified
hypothesis — but note it describes **iOS and Android**, while this repo's tooling so far
targets Android only.

**Redaction.** The original PDF contains plaintext test-account emails and passwords.
Per `CLAUDE.md` ("Secrets and machine-specific values go in `.env`, referenced by
name. Never inline a token, device serial, account..."), those have been replaced below
with `<.env: VAR_NAME>` placeholders. The real values are **not** in this repo — add them
to your local `.env` using the new entries appended to `.env.example`. See the appendix
at the end of this file for the full mapping and one discrepancy found in the source
data.

**How to use this.** Each `- [ ]` is one test case from the original "Test Cases" column;
the indented `>` line under it is the original "Comments" column. The original also had a
per-row "Status (Pass/Fail)" column — that is a run-time artifact, not part of the
checklist itself, so it is dropped here; check items off (or track pass/fail in Testmo)
when actually executing a run.

**Relevance to this repo.** This is a strong candidate cross-check for
`context/feature-map.md` (36 feature areas, all tiers currently marked judgement-only) and
for open decision #5 in `docs/PROJECT-STATE.md` ("Tier placement... business judgement").
It was not merged into `feature-map.md` automatically — that requires a human tiering call
per the P1 session rule ("do not modify context/ files" without approval).

## 1. Build sanity & fresh install

- [ ] Verify the sanity of the build (all features to be released are included in the
      final/regression build).

  > run of all merged tickets is important.

  > board — APIs environment, Firebase, MoEngage, Humbucker, etc. For Firebase

  > hCaptcha loader seen on Firebase Stage (App Check not configured there) should not
  > appear in Production.
- [ ] Check the build launches successfully after fresh installation on:
      iOS (iPhone, latest + older OS, and iPad) and Android (latest + older OS).
